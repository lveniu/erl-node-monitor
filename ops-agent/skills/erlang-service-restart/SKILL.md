# Erlang 单服务启停与重启

只负责 `mgectl start`、`mgectl stop` 和 `mgectl restart`，不分析问题或处理内存。

## 目标与动作

- 必须明确一个目标服务和一个动作；未指定服务时不得遍历或批量启停，应要求用户指定。
- “启动”只执行 `start`，“停服”只执行 `stop`，“重启”只执行 `restart`，不得自行替换动作。
- 重启必须直接使用 `mgectl restart`，不得拆成先停服再启动。
- 用户只要求分析时使用 `erlang-ops-analysis`，不得执行服务控制。

## 执行前检查

1. 调用 `list_skills` 并加载本 Skill；已加载时不要重复。
2. 通过平台校验当前服务器和真实服务目录，用最少的只读命令确认 `./mgectl`、当前 BEAM PID、节点和监听状态。
3. 按当前状态判断：
   - 启动：服务已正常运行时不重复启动，直接报告目标已满足。
   - 停服：服务已停止时不重复停服，直接报告目标已满足。
   - 重启：服务必须正在运行；已停止时不得把重启变成启动，应报告状态并让用户选择是否启动。
4. 目标、目录或状态无法确认，或有证据表明正在发布、合服或执行数据任务时停止，不提交命令。

## 固定命令

一次只允许提交以下一条命令：

```sh
cd -- '<verified-server-dir>' && ./mgectl start
cd -- '<verified-server-dir>' && ./mgectl stop
cd -- '<verified-server-dir>' && ./mgectl restart
```

必须把 `<verified-server-dir>` 替换为只读检查确认的真实目录，不得改变命令结构。

## 审批与执行

1. 检查通过后立即调用 `shell_exec`，提交与用户动作一致的一条固定命令；不得只输出命令或用文字代替工具调用。
2. 平台进入 `awaiting_approval` 后等待 Grafana Admin 决定。Admin 拒绝时记录“未执行”，不得重提、改写命令或规避审批。
3. 批准并返回结果后继续同一任务完成验证。退出码为 0 不能单独证明服务状态已经达到目标。
4. 模型返回多条工具调用时按原顺序逐条执行，不并发、不合并。

工具调用示例：

```json
{"target":"current-server","command":"cd -- '<verified-server-dir>' && ./mgectl restart","reason":"重启已确认的当前 Erlang 单服务，并验证新 PID、节点和监控状态"}
```

## 结果验证

- 启动：确认产生 BEAM PID并持续存活，目标节点、监听、Erlang RPC 和 Exporter 最新样本恢复。
- 停服：确认处理前 PID 已退出，目标节点和监听按预期消失；该节点停止造成的 Exporter 降级属于预期结果。
- 重启：确认原 PID 已退出，新 PID 不同且持续存活，目标节点、监听、Erlang RPC 和 Exporter 最新样本恢复。
- 需要节点内部复核时加载 `erlang-ops-analysis`，只使用其固定只读表达式。
- 关键证据缺失时只写“命令已执行，目标状态未完全验证”，不得报告成功。

## 停止与报告

- 权限不足、命令超时、输出截断或执行失败时立即停止，不切换服务器、不改用其他动作。
- 最终记录处理前状态、用户指定动作、审批结果、实际命令、处理后验证和未解决项。
- 没有真正调用并执行 `shell_exec` 时，不得写“等待审批”“已执行”或“已完成”。
- 单任务和未显式覆盖的命令使用系统配置的 `30m` 上限。
