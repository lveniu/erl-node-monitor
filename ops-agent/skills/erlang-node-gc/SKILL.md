# Erlang 节点受控 GC

指定服务时只检查该服务；未指定服务时检查当前服务器上的全部已发现服务。逐服完成“分析基线 → 判断 → 平台审批 → GC → 验证”，不启动、停服或重启服务。

## 使用条件

- 用户明确要求执行 GC 或优化 BEAM 内存；或者原始任务已授权必要处理，且 `erlang-ops-analysis` 的只读证据确认 processes/heap 类内存适合先尝试 GC。
- 节点必须仍可响应。ETS、Mnesia、binary、atom、code 或主机其他进程占用高时，不得用 GC 代替对应分析。
- GC 无效或内存快速回升时停止并报告，不得自动升级为启动、停服或重启。

## 执行边界

- 必须通过平台的当前内网服务器和服务目录校验。
- 每条 Shell 只操作一个已确认节点；多服场景必须逐服串行处理，禁止并发或把多个节点合并进一条命令。
- 只允许使用下列固定命令，不得改写 Erlang 表达式：

  ```sh
  cd -- '<verified-server-dir>' && ./mgectl exprs "erlang:garbage_collect()"
  ```

## 执行流程

1. 调用 `list_skills`，加载 `erlang-ops-analysis` 和本 Skill；已经加载时不要重复。
2. 确定处理范围：
   - 已指定服务或节点：只处理该目标。
   - 未指定服务或节点：使用有界只读 `find`、`ps` 和 `ls`，在平台配置的 `instance_directory` 内确认服务目录及运行中的 BEAM 节点，去重后形成稳定的待检查清单。不得扫描配置目录之外的路径。
   - 无法可靠确认清单时停止并报告，不得猜测目录或节点。
3. 按清单顺序逐服处理。先用分析 Skill 记录该节点的 BEAM RSS、`erlang:memory()` 分类、Run Queue、节点状态和最新监控样本。
4. 仅当节点可响应，且证据确认 processes/heap 类内存适合回收时才进入 GC。ETS、Mnesia、binary、atom、code、主机其他进程占用高，或目录不明确、存在已知发布/数据任务时，记录跳过原因并检查下一服。
5. 符合条件时立即调用 `shell_exec`：

   ```json
   {"target":"current-server","command":"cd -- '<verified-server-dir>' && ./mgectl exprs \"erlang:garbage_collect()\"","reason":"对已确认的当前 Erlang 节点执行一次受控 GC，并复核内存变化和节点状态"}
   ```

6. 必须把 `<verified-server-dir>` 替换为当前节点只读检查得到的真实目录。不要只输出代码块，不要用文字询问是否执行，不要在工具调用前输出最终结果。
7. 平台进入 `awaiting_approval` 后等待 Grafana Admin 决定。Admin 拒绝时记录该节点“未执行”，不得重新提交或规避审批；多服任务可继续检查下一服。
8. 批准并返回执行结果后，使用分析 Skill 重新采集该节点的 BEAM RSS、内存分类、Run Queue、节点存活和 Exporter 最新样本。只有内存下降且节点保持正常时才能记录“本次 GC 有效”；退出码为 0 不能单独证明有效。
9. 完成当前节点的判断或验证后再处理下一服。全部检查结束后汇总已检查、已跳过、等待/拒绝审批、已执行有效、已执行无效和未验证的节点。

## 停止与报告

- GC 命令超时、输出截断或执行失败时立即停止整个任务，不切换节点、不重启服务、不尝试其他 Erlang 表达式。
- 关键复核证据缺失时写“GC 已执行，效果未完全验证”，不得声称内存已优化或节点已恢复。
- 最终分开记录处理前事实、判断依据、审批结果、实际命令、处理后验证和未解决项。
- 单任务和未显式覆盖的命令使用系统配置的 `30m` 上限。
